# 作品说明与评分点对照

## 一、赛题理解

「全国高校 AI Web 开发挑战赛」考察的是：**能否用 AI 能力真正解决一个具体场景里的真实问题，而不是给传统系统贴一个聊天框**。

我们选择的场景是**高校学籍管理**——一个数据密集、规则密集、用户多角色（教务/辅导员/学生）、且对"数据准确性"极度敏感的业务。它天然适合 AI，但也天然排斥"胡说八道的 AI"。因此本作品的设计主线是：

> **让 AI 说得对、说得清、可复核。**

具体落成三条硬约束：

1. **结论必须有据**：所有涉及学生/成绩/奖惩/统计的回答，必须先调用工具取真实数据，禁止凭常识编造（见 `Prompts.system()` 工作原则）。
2. **过程必须可见**：工具调用、参数、耗时、生成的 SQL、引用的制度原文全部在前端展示。
3. **失效必须有兜底**：未配置大模型密钥时，本地规则引擎接管全部能力，功能不缺项、演示不中断。

---

## 二、与"传统系统 + 聊天框"的区别

| 常见做法 | 本作品做法 |
| --- | --- |
| 把问题拼进 prompt，让模型自由回答 | Agent 循环：模型**选择工具** → 执行 → 观测结果 → 再决定是否继续（最多 5 轮） |
| 学校数据用于"训练"或写死在提示词里 | 数据永远在数据库里，工具层是唯一的取数入口 |
| AI 生成 SQL 直接执行 | 6 道安全闸门 + 结果集会话只读连接 + 全文展示 |
| 制度问答靠模型记忆 | RAG 混合检索 + 逐条标注出处，无依据时明确说"知识库暂无该规定" |
| 用户必须会提问 | 看板/预警页由 AI **主动**跑分析并给出洞察，不等人问 |

### 3. 工程质量与安全

| 要点 | 实现 | 代码位置 |
| --- | --- | --- |
| 不破坏既有系统 | AI 模块完全独立在 `com.school.student_manage.ai`，原有控制器/服务/Mapper 零改动 | `git` 差异仅新增（+ `application.yml` 增加 `ai:` 段） |

### 5. 创新点（可重点讲述）

1. **双引擎架构**：远程大模型与本地规则引擎实现同一个 `LlmClient` 接口，路由器按可用性切换。等于给 AI 系统装了"双回路供电"，答辩现场断网/无 Key 也能完整演示（`HeuristicClient` 约 900 行，含意图识别、多工具计划、模板渲染）。
2. **数据质量自省**：AI 会主动指出数据本身的问题——成绩覆盖率仅 40%、存在超过 100 分的异常成绩、学籍状态值不统一（在读/在校）、gender 与 sex 两列冲突。这是"AI 懂业务"而非"AI 套模板"的直接证据。
3. **工具返回信封协议**：`ToolResult{render, summary, data, chart, hints}` 既喂给模型（压缩文本），又驱动前端渲染，还支撑本地兜底答案组装——一份数据三处复用。
4. **风险规则引擎 + 大模型分工**：规则负责"筛得准"（可解释、可审计），大模型负责"说得好"（分层处置建议、话术），两者结果同屏对照。

## 四、演示一句话总结

> 我们对一套真实的学籍管理系统做了 AI 原生改造：老师用一句话就能取数，制度问题有原文出处，风险学生被系统主动识别并给出帮扶方案；**所有结论都来自数据库真实数据，所有推理过程都能在界面上一眼复核**；即使没有任何大模型密钥，整套系统依然完整可用。
